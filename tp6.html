Spark sur le cluster du TP2 : calculer à plusieurs machines

Ajouter Spark au cluster de 4 machines virtuelles du TP2, répartir le calcul sur les trois workers, observer la localité des données et le shuffle sur le réseau, puis provoquer une panne et voir Spark s'en remettre.

DITI 4Diplôme d'Ingénieur en Techniques InformatiquesAnnée 2026-2027Spark 4.2.0Hadoop 3.5.0Cluster 4 nœudsVirtualBoxOctobre 2026

Objectif

Exécuter les traitements Spark du TP5 sur trois workers, et observer ce qu'un vrai cluster change : réseau, localité, pannes.

Lien avec le cours

Chapitre 6 — architecture complète de Spark, cohabitation avec Hadoop, résilience par lignage. Chapitre 2 — localité des données.

Question d'ingénieur

Que change un vrai cluster à l'exécution d'un même code (réseau, localité) et comment Spark reprend-il le calcul quand une machine tombe en panne ?

Sommaire

    Introduction

    Au TP5, Spark tournait sur une seule machine : le driver, YARN et les executors se partageaient la même VM. Les notions du chapitre 6 (executors répartis, shuffle, localité, résilience) n'y étaient visibles qu'en théorie. Ce TP reprend le cluster de 4 machines virtuelles du TP2 et y ajoute Spark :

    • Spark n'est installé que sur le master, qui devient le poste d'où l'on soumet les applications (le driver y tourne) ;
    • les trois workers ne reçoivent rien de nouveau : YARN y lance les executors dans des conteneurs, et les bibliothèques de Spark arrivent depuis HDFS ;
    • MapReduce (TP2) et Spark se partagent ainsi le même stockage (HDFS) et le même gestionnaire de ressources (YARN).
    Objectif du TP : installer Apache Spark 4.2.0 sur le master du cluster du TP2 (Hadoop 3.5.0, Java 21), exécuter les traitements du TP5 sur trois executors répartis sur trois machines, et observer la localité des données, le shuffle sur le réseau et la reprise après une panne.

    Légende : le driver reste sur le master (mode client). YARN place l'ApplicationMaster et un executor par worker. Chaque executor lit en priorité les blocs HDFS de son propre nœud (localité), et les executors échangent les données du shuffle par le réseau host-only. Le master n'a pas de NodeManager (fichier workers du TP2) : aucun executor n'y tourne.

    1. Prérequis

    1.1 Ce que vous devez avoir terminé

    • Le TP2 : cluster de 4 VM opérationnel (HDFS avec 3 DataNodes, YARN avec 3 NodeManagers).
    • Le TP5 : vous réutiliserez ses scripts (gen_ventes.py, ca_par_ville.py) et ses notions (DAG, cache, shuffle).

    1.2 Passer les machines virtuelles à 3 Go de mémoire

    Avec 2 Go par VM (TP2), un worker ne peut accueillir qu'un seul conteneur Spark, et le master n'a pas assez de mémoire pour le driver. On passe donc chaque VM à 3 Go :

    VMMémoire TP2Mémoire TP6Ce qui y tourne en plus
    hadoop-master2 Go3 Gole driver Spark (JVM + Python)
    hadoop-datanode1 à 32 Go3 Goun executor Spark par worker (et l'ApplicationMaster sur l'un d'eux)
    Total8 Go12 Goun poste de 16 Go est nécessaire
    1. Sur master, arrêtez proprement le cluster : stop-yarn.sh puis stop-dfs.sh.
    2. Éteignez les 4 VM (sudo poweroff dans chacune).
    3. Dans VirtualBox, pour chaque VM : Configuration → Système → Carte mère → Mémoire vive : 3072 Mo.
    4. Redémarrez les 4 VM.

    1.3 Vérifier la résolution des noms

    Sur un vrai cluster, le driver (sur master) et les executors (sur les workers) doivent se joindre par leurs adresses host-only. Sur chacune des 4 VM, vérifiez :

    getent hosts master datanode1 datanode2 datanode3
grep -n "127.0.1.1" /etc/hosts

    La première commande doit afficher les quatre adresses 192.168.56.10 à .13. La seconde ne doit afficher aucune ligne contenant le nom de la machine (par exemple 127.0.1.1 master) : Ubuntu en ajoute une à l'installation. Si elle existe, supprimez-la :

    sudo sed -i '/^127\.0\.1\.1/d' /etc/hosts
    Pourquoi c'est important : si master se résout en 127.0.1.1, le driver s'annonce avec cette adresse de bouclage. Les executors, sur les workers, essaient alors de s'y connecter… et tombent sur eux-mêmes. L'application reste bloquée sur « Initial job has not accepted any resources ».

    2. Remettre le cluster à niveau

    Quatre réglages, repris de l'expérience du TP5, sont à ajouter à la configuration du TP2. Les fichiers sont modifiés sur master, puis copiés vers les workers (section 2.5).

    2.1 Des dossiers de travail sur le disque (sur les 4 VM)

    Sur Ubuntu Server 26.04, /tmp est en mémoire vive (tmpfs) : il est petit, vidé à chaque redémarrage, et le TP2 y place les journaux de Hadoop. Or YARN y recopie aussi les bibliothèques de chaque application Spark (plusieurs centaines de Mo) : il serait vite saturé (« Disk quota exceeded »). On crée donc deux dossiers sur le disque, sur chacune des 4 VM :

    sudo mkdir -p /hadoop/tmp /hadoop/logs
sudo chown -R hadoop:hadoop /hadoop
df -h /tmp /hadoop

    2.2 hadoop-env.sh : les journaux sur le disque

    Sur master, dans $HADOOP_HOME/etc/hadoop :

    cd $HADOOP_HOME/etc/hadoop
sed -i 's#^export HADOOP_LOG_DIR=.*#export HADOOP_LOG_DIR=/hadoop/logs#' hadoop-env.sh
grep HADOOP_LOG_DIR hadoop-env.sh

    2.3 core-site.xml : le dossier de travail de Hadoop

    Ajoutez dans core-site.xml, à l'intérieur de <configuration> :

      <property>
    <name>hadoop.tmp.dir</name>
    <value>/hadoop/tmp</value>
  </property>

    2.4 yarn-site.xml : mémoire et réglages pour Spark

    Dans yarn-site.xml, passez les deux valeurs de mémoire du TP2 de 1536 à 2560 :

    sed -i 's#<value>1536</value>#<value>2560</value>#' yarn-site.xml
grep -B1 "2560" yarn-site.xml

    Puis ajoutez ces quatre propriétés, à l'intérieur de <configuration> :

      <property>
    <name>yarn.scheduler.minimum-allocation-mb</name>
    <value>512</value>
  </property>
  <property>
    <name>yarn.nodemanager.vmem-check-enabled</name>
    <value>false</value>
  </property>
  <property>
    <name>yarn.log-aggregation-enable</name>
    <value>true</value>
  </property>
  <property>
    <name>yarn.nodemanager.bind-host</name>
    <value>0.0.0.0</value>
  </property>
    Le calcul de la mémoire (à comprendre) : chaque worker offre désormais 2 560 Mo à YARN. Un conteneur reçoit la mémoire demandée + une marge de 384 Mo, arrondie au multiple de minimum-allocation-mb (512 Mo) supérieur :
    • executor : 1 024 + 384 = 1 408 Mo → 1 536 Mo ;
    • ApplicationMaster : 512 + 384 = 896 Mo → 1 024 Mo ;
    • le worker qui reçoit l'ApplicationMaster : 1 536 + 1 024 = 2 560 Mo, pile la capacité ; les deux autres : un executor chacun.
    Résultat : 3 executors, un par worker. Avec l'arrondi par défaut à 1 024 Mo, l'executor occuperait 2 048 Mo et le worker de l'ApplicationMaster ne pourrait plus en accueillir : on n'aurait que 2 executors.
    • vmem-check-enabled = false et log-aggregation-enable = true : mêmes raisons qu'au TP5 (section 5.1).
    • nodemanager.bind-host = 0.0.0.0 : les pages des NodeManagers (journaux des conteneurs) restent joignables depuis votre poste.

    2.5 Copier la configuration et redémarrer

    Sur master, avec la boucle du TP2 (section 7.7) :

    cd $HADOOP_HOME/etc/hadoop
for host in datanode1 datanode2 datanode3; do
  scp hadoop-env.sh core-site.xml yarn-site.xml hadoop@$host:$HADOOP_CONF_DIR/
done

start-dfs.sh
start-yarn.sh
hdfs dfsadmin -report | grep "Live datanodes"
yarn node -list

    Vous devez lire Live datanodes (3) et trois NodeManagers à l'état RUNNING. Sur http://192.168.56.10:8088/cluster/nodes, chaque nœud affiche 2.5 GB de mémoire disponible.

    Les données HDFS ne bougent pas : leurs dossiers (/hadoop/dfs) sont fixés séparément dans hdfs-site.xml depuis le TP2. Aucun nouveau formatage du NameNode n'est nécessaire.

    3. Installer Spark sur le master

    Toute cette section se fait sur master, avec l'utilisateur hadoop. Rien n'est installé sur les workers.

    3.1 Téléchargement

    cd ~
wget https://archive.apache.org/dist/spark/spark-4.2.0/spark-4.2.0-bin-hadoop3.tgz
tar -xzf spark-4.2.0-bin-hadoop3.tgz
sudo mv spark-4.2.0-bin-hadoop3 /opt/spark
sudo chown -R hadoop:hadoop /opt/spark
rm spark-4.2.0-bin-hadoop3.tgz

    3.2 Variables d'environnement

    Ajoutez à la fin de ~/.bashrc (HADOOP_HOME et HADOOP_CONF_DIR y sont déjà depuis le TP2) :

    # ---- Spark Environment Variables ----
export SPARK_HOME=/opt/spark
export PATH=$PATH:$SPARK_HOME/bin
export YARN_CONF_DIR=$HADOOP_HOME/etc/hadoop
export PYSPARK_PYTHON=python3

    source ~/.bashrc
spark-submit --version

    3.3 spark-env.sh : l'adresse du driver et l'environnement

    mkdir -p ~/tmp
cd $SPARK_HOME/conf
cp spark-env.sh.template spark-env.sh
cat >> spark-env.sh << 'EOF'
export SPARK_LOCAL_IP=192.168.56.10
export HADOOP_CONF_DIR=/opt/hadoop/etc/hadoop
export YARN_CONF_DIR=/opt/hadoop/etc/hadoop
export JAVA_HOME=$(dirname $(dirname $(readlink -f $(which java))))
export SPARK_LOCAL_DIRS=/home/hadoop/tmp
export SPARK_SUBMIT_OPTS="-Djava.io.tmpdir=/home/hadoop/tmp"
EOF
cp log4j2.properties.template log4j2.properties
sed -i 's/^rootLogger.level = info/rootLogger.level = warn/' log4j2.properties
    Pourquoi SPARK_LOCAL_IP ? Chaque VM a deux cartes réseau, et la carte NAT porte la même adresse (10.0.2.15) sur les quatre VM. Si le driver s'annonçait avec cette adresse, chaque executor se connecterait… à sa propre machine. On impose donc l'adresse host-only du master. Les autres lignes reprennent les leçons du TP5 : variables lues par Spark quel que soit le programme qui le lance (terminal, PyCharm, notebook), et fichiers temporaires hors de /tmp.

    3.4 spark-defaults.conf

    cp spark-defaults.conf.template spark-defaults.conf
nano spark-defaults.conf

    Ajoutez à la fin :

    spark.master                     yarn
spark.submit.deployMode          client
spark.driver.memory              512m
spark.executor.instances         3
spark.executor.cores             1
spark.executor.memory            1g
spark.yarn.am.memory             512m
spark.eventLog.enabled           true
spark.eventLog.dir               hdfs://master:8020/spark-logs
spark.history.fs.logDirectory    hdfs://master:8020/spark-logs
spark.yarn.historyServer.address master:18080

    3.5 Préparer HDFS : historique et bibliothèques

    Comme au TP5 (section 5.4), on dépose une seule fois les bibliothèques de Spark dans HDFS : sur un cluster, elles seraient sinon recopiées vers les trois workers à chaque application. Procédez étape par étape et vérifiez chaque résultat :

    hdfs dfs -mkdir -p /spark-logs /spark-jars

cd ~
python3 -m zipfile -c spark-libs.zip $SPARK_HOME/jars/*.jar
ls -lh spark-libs.zip
hdfs dfs -put -f spark-libs.zip /spark-jars/
hdfs dfs -ls -h /spark-jars

    Seulement si l'archive apparaît dans HDFS avec la bonne taille :

    rm ~/spark-libs.zip
echo "spark.yarn.archive               hdfs://master:8020/spark-jars/spark-libs.zip" >> $SPARK_HOME/conf/spark-defaults.conf
    Avec dfs.replication = 3, l'archive est présente sur les trois workers : chaque NodeManager la récupère localement, une fois, et la garde en cache pour les applications suivantes.

    5. Le fil rouge, distribué

    5.1 Des données réparties sur les trois workers

    Sur master, recréez purchases.txt et gen_ventes.py du TP5 (section 7.1), puis générez 6 millions de ventes, soit environ 300 Mo et 3 blocs HDFS :

    cd ~
python3 gen_ventes.py 6000000
ls -lh purchases_big.txt
hdfs dfs -mkdir -p /input
hdfs dfs -put -f purchases.txt purchases_big.txt /input/
hdfs fsck /input/purchases_big.txt -files -blocks -locations

    La dernière commande liste chaque bloc et les trois DataNodes qui en détiennent une copie (réplication ×3 du TP2).

    5.2 Le chiffre d'affaires par ville, sur trois machines

    Dans le shell pyspark resté ouvert :

    import time
big = sc.textFile("hdfs:///input/purchases_big.txt")
big.getNumPartitions()                                   # une partition par bloc
paires = big.map(lambda l: l.split("\t")).map(lambda c: (c[2], float(c[4])))
ca = paires.reduceByKey(lambda a, b: a + b)

t = time.time()
print(ca.takeOrdered(5, key=lambda t: -t[1]), round(time.time() - t, 1), "s")

    Dans l'onglet Stages de l'interface, ouvrez le premier stage du job et regardez le tableau des tâches : colonnes Executor ID / Host et Locality Level.

    6. Expérience : une machine tombe en panne

    Au chapitre 6, la résilience des RDD reposait sur le lignage : une partition perdue est recalculée à partir de sa recette. On le vérifie en arrêtant un worker en plein travail.

    6.1 Remplir le cache sur les trois executors

    paires.cache()
paires.count()        # lit HDFS et remplit le cache sur les trois executors

    Dans l'onglet Storage, notez le nombre de partitions en cache (Cached Partitions) et, dans le détail, leur répartition par executor.

    6.2 Arrêter un worker

    Dans un second terminal, sur datanode2, arrêtez son NodeManager : YARN tue aussitôt les conteneurs de ce nœud, dont un executor.

    ssh datanode2
yarn --daemon stop nodemanager
exit

    6.3 Relancer le calcul

    Revenez au shell pyspark et relancez le chiffre d'affaires :

    t = time.time()
print(paires.reduceByKey(lambda a, b: a + b).takeOrdered(5, key=lambda t: -t[1]),
      round(time.time() - t, 1), "s")

    Observez l'onglet Executors (un executor marqué Dead), l'onglet Storage (partitions en cache) et le détail du dernier stage (tâches qui ne lisent plus depuis le cache).

    Question 5 : le résultat est-il identique à celui de la section 5.2 ? Combien de partitions en cache restait-il après la panne, et comment Spark a-t-il obtenu les autres ? Pourquoi le nombre d'executors ne remonte-t-il pas à trois (aidez-vous du calcul de mémoire de la section 2.4) ? Comparez cette résilience par recalcul à la résilience par réplication de HDFS : que coûte chacune ?

    6.4 Remettre le worker en service

    ssh datanode2
yarn --daemon start nodemanager
exit
yarn node -list

    Le DataNode de datanode2 n'a jamais été arrêté : HDFS est resté complet. Pour aller plus loin : arrêtez aussi le DataNode (hdfs --daemon stop datanode) sur purchases_r1.txt (une seule copie) et expliquez ce qui se passe.

    Quittez le shell (exit()) : le cache et les executors sont libérés.

    10. Résolution des problèmes courants (Dépannage)

    SymptômeCause probableSolution
    L'application reste sur « Initial job has not accepted any resources »Les executors ne joignent pas le driver : adresse annoncée en 127.0.1.1 ou 10.0.2.15Vérifiez SPARK_LOCAL_IP=192.168.56.10 (section 3.3) et l'absence de ligne 127.0.1.1 dans /etc/hosts (section 1.3).
    Seulement 2 executors au lieu de 3Mémoire YARN insuffisante ou arrondi à 1 024 MoVérifiez memory-mb = 2560 et minimum-allocation-mb = 512 sur les 4 nœuds (section 2.4), puis redémarrez YARN.
    L'application reste en état ACCEPTEDUne autre application Spark (shell, notebook) occupe les conteneursFermez-la (exit(), spark.stop()) ou yarn application -kill <id>.
    « Disk quota exceeded » ou « No space left on device »Fichiers temporaires dans /tmp (tmpfs)Sections 2.1 à 2.3 sur les 4 nœuds et section 3.3 sur master ; nettoyez /tmp/spark-* et /tmp/hadoop-hadoop.
    « File does not exist: …/spark-libs.zip »La ligne spark.yarn.archive a été ajoutée sans que l'archive soit dans HDFSsed -i '/spark.yarn.archive/d' $SPARK_HOME/conf/spark-defaults.conf, puis refaites la section 3.5 étape par étape.
    Conteneur tué : « running beyond virtual memory limits »Contrôle de la mémoire virtuellevmem-check-enabled = false sur les 4 nœuds (section 2.4).
    Erreur Python dans les executors : « Python in worker has different version »Version de Python différente entre master et un workerpython3 --version sur les 4 VM : toutes doivent être en 3.14 (Ubuntu Server 26.04).
    Un NodeManager n'apparaît plus dans yarn node -listArrêté à la section 6, ou VM éteinteyarn --daemon start nodemanager sur le worker concerné.
