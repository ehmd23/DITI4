Installer Apache Spark sur la VM du TP1 et calculer en mémoire

Ajouter Spark au Hadoop pseudo-distribué du TP1 : HDFS stocke, YARN loue les ressources, Spark calcule. Puis refaire le chiffre d'affaires par ville en RDD et observer jobs, stages, shuffle et cache.

DITI 4Diplôme d'Ingénieur en Techniques InformatiquesAnnée 2026-2027Spark 4.2.0Hadoop 3.5.0 (TP1)Java 21Python 3Octobre 2026

Objectif

Installer Spark sur la VM du TP1, l'exécuter sur YARN et lire un traitement RDD dans l'interface web (port 4040).

Lien avec le cours

Chapitre 6 — Spark : architecture, RDD, transformations et actions, DAG, cache, cohabitation avec Hadoop.

Question d'ingénieur

Comment un moteur en mémoire s'insère-t-il dans le cluster Hadoop déjà en place (même stockage, mêmes ressources) et que change-t-il à l'exécution ?

Sommaire

    Introduction

    Au TP1, vous avez installé HDFS et YARN sur une seule machine. Ce TP en est la suite directe : on ajoute Apache Spark sur la même VM, avec le même utilisateur hadoop, sans rien réinstaller. Spark ne remplace ni HDFS ni YARN : il remplace seulement le moteur de calcul MapReduce.

    • HDFS continue de stocker les fichiers (les blocs de 128 Mo du chapitre 3).
    • YARN continue de louer CPU et mémoire : il lance les executors Spark dans des conteneurs.
    • Spark exécute votre code Python : le driver construit le DAG et envoie les tâches aux executors.
    Objectif du TP : installer Apache Spark 4.2.0 sur la VM Ubuntu Server 26.04 du TP1 (Hadoop 3.5.0, Java 21), l'exécuter en mode local puis sur YARN, et retrouver dans l'interface web tout ce qui a été vu au chapitre 6.

    2. Téléchargement et installation de Spark 4.2.0

    On télécharge la distribution binaire pré-compilée pour Hadoop 3, comme pour Hadoop au TP1 :

    # Téléchargement (plusieurs centaines de Mo)
cd ~
wget https://archive.apache.org/dist/spark/spark-4.2.0/spark-4.2.0-bin-hadoop3.tgz

# Extraction
tar -xzf spark-4.2.0-bin-hadoop3.tgz

# Déplacement vers /opt, à côté de /opt/hadoop
sudo mv spark-4.2.0-bin-hadoop3 /opt/spark

# Attribution des droits à l'utilisateur hadoop
sudo chown -R hadoop:hadoop /opt/spark

    Vérification rapide :

    ls /opt/spark

    Vous devez voir notamment les dossiers bin, conf, examples, jars, python et sbin.

    Pas de nouveau démon : contrairement à Hadoop, on ne « démarre » pas Spark. Spark est ici un client : chaque application demande ses ressources à YARN quand elle démarre, et les rend quand elle se termine. N'utilisez pas les scripts /opt/spark/sbin/start-all.sh : ils lancent un cluster Spark Standalone, que nous n'utilisons pas (et qui porte le même nom que le script de Hadoop).

    3. Configuration des variables d'environnement

    Éditez à nouveau le fichier .bashrc de l'utilisateur hadoop :

    nano ~/.bashrc

    Ajoutez ces lignes à la fin du fichier, après le bloc Hadoop du TP1 :

    # ---- Spark Environment Variables ----
export SPARK_HOME=/opt/spark
export PATH=$PATH:$SPARK_HOME/bin
export HADOOP_CONF_DIR=$HADOOP_HOME/etc/hadoop
export YARN_CONF_DIR=$HADOOP_HOME/etc/hadoop
export PYSPARK_PYTHON=python3
export PYSPARK_DRIVER_PYTHON=python3

    Appliquez et testez :

    source ~/.bashrc
spark-submit --version

    Vous devez voir le logo Spark et la ligne version 4.2.0.

    Pourquoi HADOOP_CONF_DIR ? C'est par là que Spark trouve core-site.xml (adresse de HDFS : hdfs://localhost:8020) et yarn-site.xml (adresse du ResourceManager). Sans cette variable, --master yarn échoue avec le message « HADOOP_CONF_DIR or YARN_CONF_DIR must be set ». On n'ajoute volontairement que $SPARK_HOME/bin au PATH, pas $SPARK_HOME/sbin : voir l'encadré de la section 2.

    3.1 Une console plus lisible (recommandé)

    Par défaut, Spark affiche beaucoup de messages INFO. Gardez seulement les avertissements :

    cd $SPARK_HOME/conf
cp log4j2.properties.template log4j2.properties
sed -i 's/^rootLogger.level = info/rootLogger.level = warn/' log4j2.properties

    3.2 Fixer le nom d'hôte utilisé par Spark (obligatoire)

    Pour que ses composants se parlent, Spark construit des adresses du type spark://…@nom-de-la-machine:port, à partir du nom réseau de la VM. Or ce nom est souvent invalide pour Java dans une VM : par exemple ubuntu-26.04--with-rosetta-.shared sous Parallels (un élément du nom se termine par un tiret). Spark refuse alors de démarrer avec l'erreur « Invalid Spark URL: spark://HeartbeatReceiver@… ». Comme tout le TP se déroule sur une seule machine, on indique à Spark d'utiliser simplement localhost :

    cd $SPARK_HOME/conf
cp spark-env.sh.template spark-env.sh
echo 'export SPARK_LOCAL_HOSTNAME=localhost' >> spark-env.sh
tail -1 spark-env.sh
    Pour comprendre : affichez le nom de votre VM avec hostname et hostname -f. Un nom d'hôte valide ne contient que des lettres, des chiffres et des tirets, sans tiret au début ou à la fin de chaque partie. Le fichier spark-env.sh est lu à chaque lancement de pyspark ou spark-submit : le réglage s'applique donc aussi au mode YARN (section 5).

    4. Premier test en mode local

    Avant d'utiliser YARN, on vérifie Spark seul : en mode local[2], driver et executor sont dans un seul processus, avec 2 cœurs.

    pyspark --master "local[2]"

    Le shell PySpark s'ouvre ; la variable sc (le SparkContext) existe déjà. Tapez :

    rdd = sc.parallelize([1, 2, 3, 4, 5, 6])
rdd.map(lambda x: x * 10).collect()          # [10, 20, 30, 40, 50, 60]
rdd.filter(lambda x: x % 2 == 0).count()     # 3

    Pendant que le shell est ouvert, ouvrez l'interface web de l'application : http://localhost:4040 (depuis votre poste, préparez d'abord le tunnel décrit en 4.1). Dans l'onglet Jobs, vous voyez 2 jobs : un par action (collect, count). Quittez le shell avec exit() (ou Ctrl+D).

    Si les résultats s'affichent et que l'interface 4040 montre vos deux jobs, Spark est correctement installé.

    4.1 Ouvrir les interfaces web depuis votre poste

    Ubuntu Server n'a pas de navigateur : on consulte les interfaces depuis la machine hôte. Or, avec SPARK_LOCAL_HOSTNAME=localhost (section 3.2), l'interface d'une application Spark n'écoute que dans la VM :

    ss -lntp | grep 4040        # LISTEN ... 127.0.0.1:4040 : joignable seulement depuis la VM

    On la rend accessible depuis votre poste par un tunnel SSH. Notez d'abord l'adresse IP de la VM (hostname -I dans la VM), puis, dans un terminal de votre poste (pas de la VM), laissez tourner :

    ssh -N -L 4040:localhost:4040 -L 18080:localhost:18080 hadoop@IP_DE_LA_VM

    Tant que cette commande tourne, http://localhost:4040 (application en cours) et http://localhost:18080 (historique, section 10) s'ouvrent dans le navigateur de votre poste. Arrêtez le tunnel avec Ctrl+C.

    Sur YARN (à partir de la section 6), un second chemin : le ResourceManager sert de relais vers l'interface de chaque application. Ouvrez http://IP_DE_LA_VM:8088, cliquez sur votre application puis sur ApplicationMaster, ou tapez directement http://IP_DE_LA_VM:8088/proxy/application_…/. Dans ce TP, toutes les adresses http://localhost:… s'entendent depuis la VM, ou depuis votre poste avec le tunnel ci-dessus.

    5. Configurer Spark pour YARN

    5.1 Quatre réglages côté YARN

    Éditez le yarn-site.xml du TP1 :

    nano $HADOOP_HOME/etc/hadoop/yarn-site.xml

    Ajoutez ces quatre propriétés à l'intérieur de <configuration>, après celles du TP1 :

        <property>
      <name>yarn.nodemanager.vmem-check-enabled</name>
      <value>false</value>
    </property>
    <property>
      <name>yarn.log-aggregation-enable</name>
      <value>true</value>
    </property>
    <property>
      <name>yarn.nodemanager.hostname</name>
      <value>localhost</value>
    </property>
    <property>
      <name>yarn.nodemanager.bind-host</name>
      <value>0.0.0.0</value>
    </property>
    • vmem-check-enabled = false : YARN tue par défaut un conteneur dont la mémoire virtuelle dépasse 2,1 fois sa mémoire réelle. Les JVM Java 21 réservent beaucoup de mémoire virtuelle : sans ce réglage, vos executors seraient tués au démarrage (« running beyond virtual memory limits »). La limite de mémoire réelle, elle, reste contrôlée.
    • log-aggregation-enable = true : à la fin d'une application, YARN rassemble les journaux de tous ses conteneurs dans HDFS ; la commande yarn logs (section 9) permet alors de les lire.
    • nodemanager.hostname = localhost : YARN transmet aux executors Spark le nom du nœud où tourne leur conteneur. Par défaut, c'est le nom réseau de la VM, souvent invalide (même problème qu'en section 3.2). Les executors ne parviennent alors pas à s'enregistrer auprès du driver, et l'application reste bloquée sur « Initial job has not accepted any resources ». Sur une seule machine, localhost règle la question, comme pour le reste de la configuration du TP1.
    • nodemanager.bind-host = 0.0.0.0 : le NodeManager reste joignable depuis l'extérieur de la VM (journaux des conteneurs consultés depuis l'interface 8088).

    Redémarrez YARN pour prendre en compte les changements :

    stop-yarn.sh
start-yarn.sh

    5.2 Le fichier spark-defaults.conf

    Ce fichier fixe les valeurs par défaut de toutes vos applications Spark :

    cd $SPARK_HOME/conf
cp spark-defaults.conf.template spark-defaults.conf
nano spark-defaults.conf

    Ajoutez à la fin :

    spark.master                     yarn
spark.submit.deployMode          client
spark.executor.instances         2
spark.executor.cores             1
spark.executor.memory            512m
spark.yarn.am.memory             512m
spark.eventLog.enabled           true
spark.eventLog.dir               hdfs://localhost:8020/spark-logs
spark.history.fs.logDirectory    hdfs://localhost:8020/spark-logs
spark.yarn.historyServer.address localhost:18080
    Le calcul de la mémoire (à comprendre) : au TP1, le NodeManager dispose de 4096 Mo (yarn.nodemanager.resource.memory-mb). Chaque conteneur reçoit la mémoire demandée + une marge de 384 Mo, arrondie au multiple de 1024 Mo supérieur (minimum d'allocation de YARN) :
    • executor : 512 + 384 = 896 Mo → 1024 Mo, deux fois ;
    • ApplicationMaster : 512 + 384 = 896 Mo → 1024 Mo ;
    • total : 3072 Mo sur 4096. Le driver, lui, tourne hors de YARN, dans votre session.
    VM de 4 Go (NodeManager réglé à 2048 Mo au TP1) : mettez spark.executor.instances 1.

    5.3 Le dossier de l'historique dans HDFS

    Avec spark.eventLog.enabled, chaque application écrit son journal d'exécution dans HDFS. Le dossier doit exister avant la première application :

    hdfs dfs -mkdir -p /spark-logs
hdfs dfs -ls /

    5.4 Protéger /tmp et envoyer les bibliothèques de Spark une fois pour toutes

    Sur Ubuntu Server 26.04, /tmp n'est pas sur le disque : c'est un espace en mémoire vive (tmpfs), de petite taille et limité par utilisateur. Vérifiez :

    df -h /tmp ~        # /tmp : « tmpfs », quelques Go au plus ; ~ : le disque de la VM

    Or Spark et YARN y écrivent par défaut leurs fichiers temporaires, dont une archive de toutes les bibliothèques de Spark ($SPARK_HOME/jars, plusieurs centaines de Mo) recréée à chaque application. C'est le sens de l'avertissement « Neither spark.yarn.jars nor spark.yarn.archive is set ». Après quelques lancements, /tmp est plein et Spark échoue avec « Disk quota exceeded », alors que le disque a encore de la place. On règle le problème en trois étapes.

    Étape 1 — Les fichiers temporaires de Spark sur le disque

    mkdir -p ~/tmp
cat >> $SPARK_HOME/conf/spark-env.sh << 'EOF'
export SPARK_LOCAL_DIRS=/home/hadoop/tmp
export SPARK_SUBMIT_OPTS="-Djava.io.tmpdir=/home/hadoop/tmp"
EOF

    Étape 2 — Les fichiers temporaires de Hadoop sur le disque

    YARN copie lui aussi les bibliothèques de chaque application dans son dossier de travail, par défaut sous /tmp (propriété hadoop.tmp.dir). Si votre core-site.xml ne contient pas déjà hadoop.tmp.dir (ajouté au TP1, section 6.2), arrêtez le cluster et ajoutez-la :

    stop-all.sh
mkdir -p ~/hadoop-tmp
nano $HADOOP_HOME/etc/hadoop/core-site.xml

        <property>
        <name>hadoop.tmp.dir</name>
        <value>/home/hadoop/hadoop-tmp</value>
    </property>

    start-all.sh
jps

    Les données HDFS ne bougent pas : leurs dossiers (/home/hadoop/hdfs) sont fixés séparément depuis le TP1.

    Étape 3 — Déposer les bibliothèques de Spark une seule fois dans HDFS

    Procédez étape par étape et vérifiez chaque résultat avant de passer à la suivante :

    cd ~
python3 -m zipfile -c spark-libs.zip $SPARK_HOME/jars/*.jar      # quelques dizaines de secondes
ls -lh spark-libs.zip                                              # plusieurs centaines de Mo

hdfs dfs -mkdir -p /spark-jars
hdfs dfs -put -f spark-libs.zip /spark-jars/
hdfs dfs -ls -h /spark-jars                                        # l'archive est-elle là ?

    Seulement si spark-libs.zip apparaît dans HDFS avec la bonne taille, supprimez la copie locale et déclarez l'archive à Spark :

    rm ~/spark-libs.zip
echo "spark.yarn.archive               hdfs://localhost:8020/spark-jars/spark-libs.zip" >> $SPARK_HOME/conf/spark-defaults.conf
    Attention à l'ordre : si la ligne spark.yarn.archive est ajoutée alors que l'archive n'est pas dans HDFS, plus aucune application ne démarre (« File does not exist: …/spark-libs.zip »).

    L'avertissement disparaît et les applications démarrent plus vite : YARN réutilise l'archive déjà présente dans HDFS.

    À partir d'ici, pyspark et spark-submit utilisent YARN par défaut (spark.master yarn). Pour revenir au mode local, ajoutez explicitement --master "local[2]".

    7.5 Le cache, mesuré

    On chronomètre la même action deux fois sans cache, puis trois fois avec cache :

    import time

def chrono(rdd):
    t = time.time()
    n = rdd.count()
    print(n, "lignes en", round(time.time() - t, 1), "s")

chrono(paires)      # 1. sans cache
chrono(paires)      # 2. sans cache
paires.cache()
chrono(paires)      # 3. avec cache
chrono(paires)      # 4. avec cache
chrono(paires)      # 5. avec cache

    7.6 reduceByKey contre groupByKey

    Deux façons d'obtenir le même chiffre d'affaires par ville :

    r1 = paires.reduceByKey(lambda a, b: a + b).collect()

    8. Le fil rouge dans PyCharm : interpréteur SSH et notebook

    Le shell pyspark est pratique pour explorer, mais on n'y garde pas son travail. On passe maintenant à un vrai environnement de développement : PyCharm, installé sur votre poste, qui exécute le code dans la VM grâce à un interpréteur SSH.

    8.1 Le principe

    • PyCharm (sur votre poste) se connecte en SSH à la VM avec l'utilisateur hadoop.
    • Il envoie vos fichiers dans un dossier de la VM et y lance le Python de la VM.
    • Ce Python devient le driver Spark : il soumet l'application à YARN, exactement comme pyspark.

    Rien ne s'exécute sur votre poste : PyCharm n'est qu'une fenêtre sur la VM.

    Prérequis :
    • PyCharm avec la prise en charge des interpréteurs distants (SSH). Si votre version ne propose pas l'option On SSH, demandez la licence gratuite du JetBrains Student Pack avec votre adresse e-mail de l'école.
    • Un accès SSH à la VM depuis votre poste : ssh hadoop@IP_DE_LA_VM doit fonctionner (hostname -I dans la VM donne son adresse). Sous VirtualBox avec une seule carte NAT, ajoutez une redirection de port (hôte 2222 → invité 22) et utilisez le port 2222 ; avec une carte host-only, utilisez directement l'adresse IP.

    8.2 Préparer un environnement Python dans la VM

    PyCharm a besoin d'installer quelques paquets (dont Jupyter) dans l'interpréteur qu'il utilise. Sur Ubuntu Server 26.04, pip refuse d'installer dans le Python du système (« externally-managed-environment ») : on crée donc un environnement virtuel réservé au TP, dans la VM, avec l'utilisateur hadoop :

    sudo apt install -y python3-venv
python3 -m venv ~/venv-tp5
~/venv-tp5/bin/pip install jupyterlab
~/venv-tp5/bin/python --version      # même version que python3 : 3.14
    On n'installe pas pyspark avec pip. PySpark est déjà fourni par /opt/spark ; une seconde copie risquerait d'avoir une autre version que Spark. On indique plutôt à l'environnement virtuel où le trouver.

    Un fichier .pth placé dans l'environnement ajoute les dossiers de PySpark au chemin de recherche de Python, à chaque démarrage : le notebook, les scripts et l'analyse du code de PyCharm trouvent alors pyspark.

    SITE=$(~/venv-tp5/bin/python -c "import site; print(site.getsitepackages()[0])")
printf '%s\n' /opt/spark/python /opt/spark/python/lib/py4j-0.10.9.9-src.zip > $SITE/spark.pth
~/venv-tp5/bin/python -c "import pyspark; print(pyspark.__version__)"     # 4.2.0

    Reste un piège : PyCharm lance Python par SSH sans lire ~/.bashrc, donc sans les variables de la section 3. Spark échouerait avec « HADOOP_CONF_DIR or YARN_CONF_DIR must be set ». Plutôt que de les recopier dans chaque notebook et chaque configuration de PyCharm, on les place dans spark-env.sh, que Spark lit à chaque démarrage, quel que soit le programme qui le lance :

    cat >> /opt/spark/conf/spark-env.sh << 'EOF'
export HADOOP_CONF_DIR=/opt/hadoop/etc/hadoop
export YARN_CONF_DIR=/opt/hadoop/etc/hadoop
export JAVA_HOME=$(dirname $(dirname $(readlink -f $(which java))))
EOF
tail -4 /opt/spark/conf/spark-env.sh
    JAVA_HOME est recalculé à chaque démarrage à partir du Java actif de la VM : Java 21 ou Java 17 (section 10 du TP1), amd64 ou arm64, sans chemin à écrire à la main. SPARK_HOME n'est pas nécessaire : PySpark le retrouve à partir de son propre emplacement, /opt/spark/python (fichier spark.pth).

    8.3 Configurer l'interpréteur SSH dans PyCharm

    1. Créez un projet tp5-spark sur votre poste.
    2. Ouvrez le sélecteur d'interpréteur (en bas à droite) puis Add New Interpreter → On SSH.
    3. Renseignez l'hôte (IP_DE_LA_VM), le port (22, ou 2222 avec une redirection de port) et l'utilisateur hadoop, puis le mot de passe ou votre clé SSH.
    4. Quand PyCharm demande l'environnement, choisissez un interpréteur existant (Existing) : /home/hadoop/venv-tp5/bin/python.
    5. Dans Sync folders, remplacez le dossier proposé dans /tmp par /home/hadoop/tp5-spark : vos fichiers y resteront entre deux séances.
    6. Acceptez l'envoi automatique des fichiers (Auto-upload) : chaque enregistrement est copié dans la VM.
    7. Vérifiez que from pyspark.sql import SparkSession n'est pas souligné en rouge dans l'éditeur. PyCharm analyse l'interpréteur distant au moment où on le crée : si le fichier spark.pth (section 8.2) a été ajouté après, actualisez cette analyse (réglages de l'interpréteur, ou File → Invalidate Caches… → Invalidate and Restart).

    Les libellés exacts peuvent varier selon la version de PyCharm.

    8.4 Le notebook du fil rouge

    Dans le projet, créez un notebook tp5_fil_rouge.ipynb (New → Jupyter Notebook) et vérifiez qu'il utilise bien l'interpréteur SSH. Première cellule, pour vérifier où tourne le code :

    import socket, sys
print(socket.gethostname())   # le nom de la VM, pas celui de votre poste
print(sys.executable)         # /home/hadoop/venv-tp5/bin/python
    « Le notebook se connecte à localhost:54237, pas à l'IP de la VM ? » C'est normal. PyCharm démarre le serveur Jupyter dans la VM, puis crée un tunnel SSH vers un port libre de votre poste (le numéro change à chaque fois). localhost:54237 est l'entrée de ce tunnel côté poste : la cellule ci-dessus prouve que le code s'exécute bien dans la VM.

    Grâce à spark.pth et spark-env.sh (section 8.2), la deuxième cellule se contente de créer la session Spark sur YARN :

    from pyspark.sql import SparkSession
spark = SparkSession.builder.appName("TP5 - notebook").getOrCreate()
sc = spark.sparkContext
print(sc.master, sc.applicationId)   # yarn application_...
    spark-defaults.conf (YARN), spark-env.sh (nom d'hôte, Hadoop, Java) et spark.pth (PySpark) sont lus automatiquement : le notebook se comporte exactement comme le shell pyspark.

    Reprenez ensuite dans le notebook, une étape par cellule, le fil rouge de la section 7 : chargement de purchases_big.txt (7.2), chiffre d'affaires par ville (7.4) et une des analyses de la section 7.7, suivie de son commentaire technique (plan, temps) dans une cellule de texte (Markdown). L'interface de l'application s'ouvre comme en section 4.1, par le tunnel ou par le relais YARN (8088). Dernière cellule, toujours :

    spark.stop()     # rend les conteneurs à YARN
    Un notebook garde son application ouverte. Tant que le noyau tourne, les executors occupent leurs conteneurs YARN. Avec 4096 Mo pour YARN, une seule application peut tourner à la fois : sans spark.stop() (ou un redémarrage du noyau), le shell pyspark ou le spark-submit suivant reste bloqué en état ACCEPTED.

    8.5 Un script et le débogueur : driver ou executor ?

    Créez dans le projet un fichier debug_driver.py :

    from pyspark.sql import SparkSession

spark = SparkSession.builder.appName("TP5 - débogueur").getOrCreate()
sc = spark.sparkContext

def extraire(champs):
    return (champs[2], float(champs[4]))        # point d'arrêt B

    Aucune variable d'environnement n'est à saisir dans la configuration d'exécution de PyCharm : spark-env.sh (section 8.2) s'en charge.

    Lancez le script avec Run : le top 3 s'affiche dans la console de PyCharm et l'application apparaît dans YARN (8088). Placez ensuite deux points d'arrêt et lancez avec Debug :

    • A sur la ligne ca = paires.reduceByKey(…) ;
    • B sur la ligne return …, à l'intérieur de la fonction extraire, que Spark applique à chaque ligne du fichier.

    9. Passer du shell à une application

    En production, on ne tape pas les commandes dans un shell : on soumet un script avec spark-submit, exactement comme hadoop jar au TP2. Créez le fichier ca_par_ville.py :

    nano ~/ca_par_ville.py

    #!/usr/bin/env python3
"""TP5 — Chiffre d'affaires par ville en RDD, soumis à YARN avec spark-submit."""
import sys

from pyspark import SparkConf, SparkContext

entree, sortie = sys.argv[1], sys.argv[2]
sc = SparkContext(conf=SparkConf().setAppName("TP5 - CA par ville"))
sc.setLogLevel("WARN")

lignes = sc.textFile(entree)
ca = (lignes.map(lambda l: l.split("\t"))
            .filter(lambda c: len(c) == 6)
            .map(lambda c: (c[2], float(c[4])))
            .reduceByKey(lambda a, b: a + b))

ca.map(lambda t: f"{t[0]}\t{t[1]:.2f}").saveAsTextFile(sortie)

print("Top 5 des villes par chiffre d'affaires :")
for ville, montant in ca.takeOrdered(5, key=lambda t: -t[1]):
    print(f"  {ville:<16}{montant:>14,.2f}")
sc.stop()

    Le script crée lui-même son SparkContext (dans le shell, il existait déjà) et reçoit l'entrée et la sortie HDFS en arguments.

    9.1 Mode client

    spark-submit --deploy-mode client ~/ca_par_ville.py \
    hdfs:///input/purchases_big.txt hdfs:///output-spark-ca

hdfs dfs -ls /output-spark-ca
hdfs dfs -cat /output-spark-ca/part-* | head -5

    Le top 5 s'affiche directement dans votre terminal, et le résultat complet est écrit dans HDFS, au même format (ville⇥montant) que la sortie du job MapReduce du TP2.

    9.2 Mode cluster

    spark-submit --deploy-mode cluster --driver-memory 512m ~/ca_par_ville.py \
    hdfs:///input/purchases_big.txt hdfs:///output-spark-ca-cluster

    En mode cluster, le driver devient lui-même un conteneur YARN (il remplace l'ApplicationMaster) : --driver-memory 512m lui donne la même taille que les autres conteneurs, pour rester dans les 4096 Mo du NodeManager.

    Cette fois, le top 5 n'apparaît pas dans le terminal. Notez l'identifiant de l'application affiché (application_…) ou retrouvez-le sur http://localhost:8088, puis lisez la sortie du driver :

    yarn logs -applicationId application_XXXXXXXXXXXXX_XXXX -log_files stdout
    Question 7 : où le driver s'exécute-t-il dans chaque mode ? Pourquoi le print n'apparaît-il pas dans votre terminal en mode cluster ? Lequel des deux modes choisiriez-vous pour un traitement planifié chaque nuit, et pourquoi ?
    Sortie existante : comme avec MapReduce, Spark refuse d'écrire dans un dossier HDFS qui existe déjà (« Output directory … already exists »). Supprimez-le d'abord : hdfs dfs -rm -r -f /output-spark-ca.

    10. L'historique des applications

    L'interface 4040 disparaît quand l'application se termine. Le serveur d'historique relit les journaux écrits dans /spark-logs (section 5.3) et permet de revoir le DAG, les stages et le cache d'une application terminée :

    $SPARK_HOME/sbin/start-history-server.sh
jps        # un processus HistoryServer apparaît

    Ouvrez http://localhost:18080 : toutes vos applications (shells PySpark, Pi, ca_par_ville.py) y figurent. Dans l'interface YARN (8088), le lien History d'une application Spark terminée mène désormais ici.
